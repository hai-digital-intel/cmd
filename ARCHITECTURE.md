# ARCHITECTURE.md

## Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 16, App Router, React 19, TypeScript 5.9 (strict) | Server Components read straight from Prisma; Server Actions replace a hand-rolled REST layer. |
| Styling | Tailwind CSS v4 (CSS-first `@theme`) | No `tailwind.config.js` needed; design tokens live in `app/globals.css`. |
| UI primitives | Hand-rolled shadcn-style components in `components/ui` (Radix primitives + `class-variance-authority` + `tailwind-merge`) | The interactive `shadcn` CLI needs a TTY this environment doesn't have; the resulting files are structurally identical to what it generates. |
| Database | Prisma ORM 7 + SQLite, via `@prisma/adapter-better-sqlite3` | Prisma 7 requires a driver adapter at runtime (see below); SQLite needs zero external services. |
| Validation/forms | Zod 4, React Hook Form | Where a real form exists (most mutations are small enough to be plain controlled inputs calling a Server Action directly). |
| Charts | Recharts (one chart, deliberately — the category-readiness bar chart) | Anything more would violate the "no giant tables/no excessive charts" brief. |
| Dependency graph | `@xyflow/react` | The maintained successor package to what the brief calls "React Flow." |
| Tests | Vitest + Testing Library | Fast, ESM-native, no separate babel/jest config needed alongside Vite/Next tooling. |

No external services, no required API keys, no cloud database.

## Why Prisma 7 needed extra plumbing

Prisma ORM 7 removed the `url` field from `datasource` blocks in `schema.prisma` and now
requires an explicit driver adapter at runtime — there is no more "just works" Rust query
engine fallback. Concretely:

- `prisma.config.ts` (project root) tells the **CLI** (migrate, studio) where the database is.
- `lib/db/client.ts` constructs the **app's own** `PrismaClient` with a
  `PrismaBetterSqlite3` adapter, reading the same `DATABASE_URL`.
- The generator in `prisma/schema.prisma` outputs to `./generated/prisma` (gitignored,
  regenerated by `npm install`'s `postinstall` hook) rather than `node_modules/@prisma/client`
  — this is now required, not optional, in Prisma 7's `prisma-client` generator.

If you see `Error: Prisma schema validation ... datasource property 'url' is no longer
supported`, that's this exact change — it means something re-added a `url =` line to the
`datasource` block in `schema.prisma` by mistake.

## The scoring layer (`lib/services/*`)

This is the part of the app that makes it a "dependency-aware completion engine" rather than
a checklist, and it's deliberately isolated from Prisma:

```
lib/types.ts          — plain string-literal types mirroring the Prisma enums (TaskStatus, etc.)
lib/services/
  dependency.ts        — isTaskActionable, computeCriticalPathIds, cycle detection
  readiness.ts         — weighted readiness (never completed/total)
  launchGates.ts        — milestone completion + gate READY/NOT_READY/NEEDS_CONFIRMATION
  prioritization.ts     — "Your Next 3" / 15-minute-wins scoring
  timeline.ts            — critical-path effort → projected ready date
  cost.ts                 — setup-spend aggregation
  milestoneStatus.ts       — milestone node status for Roadmap/Setup Map
  graphLayout.ts            — dependency-aware layered layout for the React Flow map
  copilot.ts                 — deterministic Setup Copilot answers
```

Every function here takes and returns plain objects/arrays — no Prisma types, no database
access. `tests/services/*.test.ts` constructs fixtures with plain object literals and asserts
against them directly; nothing in that test suite touches SQLite. `lib/data/domain.ts` and
`lib/data/computed.ts` are the only places that join Prisma's relational rows into the flat
shapes these functions expect (`ScoredTask`, `ScoredMilestone`, etc.) — if you're adding a new
scoring rule, it almost certainly belongs in `lib/services`, not inline in a page or component.

### The rules that matter most

- **Readiness** is `Σ(effectiveWeight of DONE tasks) / Σ(effectiveWeight of tasks where status
  ≠ NOT_APPLICABLE)` — never a raw completed/total task count. `effectiveWeight` is
  `category.weight × milestone.weight × task.weight`, set during seeding/editing so a business
  bank account and a favicon don't count the same.
- **NOT_APPLICABLE** tasks are excluded from the denominator entirely (can't reduce
  readiness). **NEEDS_CONFIRMATION** tasks stay in the denominator but never count as done.
- **Actionability**: a task is actionable only if every task it depends on is DONE or
  NOT_APPLICABLE, and it isn't itself BLOCKED or WAITING_EXTERNAL. This is computed on every
  read — finishing a prerequisite makes downstream work actionable automatically; nothing is
  ever auto-completed.
- **Critical path** = every `requiredForLaunch` task plus the full transitive closure of its
  prerequisites (a BFS backward through `dependsOnIds`).
- **Launch gates**: a gate is READY only when every `requiredForLaunch` milestone in its
  categories is complete (all non-optional, non-N/A tasks DONE). Optional tasks/milestones
  never block a gate — this is enforced by `verificationLevel === "OPTIONAL"` being excluded
  from the completion check in `computeMilestoneCompletion`.
- **"Your Next 3"** filters to actionable tasks first, then scores by: critical-path
  membership, `requiredForLaunch`, downstream unlock count, deadline proximity, the task's own
  effective weight, a low-effort bonus, a capped age bonus, and a heavy penalty for
  WAITING_EXTERNAL (BLOCKED tasks are excluded before scoring even runs). A manual
  `priorityOverride` always wins. See `lib/services/prioritization.ts` for the exact weights
  and the reasoning behind each one — they're documented inline since they're the one part of
  this codebase intended to be retuned without a design discussion.

## Data flow for a mutation

1. A client component calls a `"use server"` action in `lib/actions/*` directly (no fetch,
   no API route — this is a Server Action, not a REST endpoint).
2. The action writes via `prisma`, optionally writes an `Activity` row via
   `lib/actions/activity.ts`, then calls `revalidatePath(...)` for every route whose data could
   have changed.
3. Next.js re-renders the affected Server Components on next navigation/refresh with fresh
   data. `router.refresh()` is used in a few client components (Focus Mode, the status select)
   to force an immediate re-fetch without a full navigation.

File uploads are the one exception that needs streaming rather than a plain Server Action
return value: `app/api/documents/[id]/file/route.ts` serves uploaded files, and
`lib/storage.ts` generates a uuid-based filename server-side for every upload — the original
filename is kept only as metadata in the `Document` row, never used as a filesystem path, which
is the entire path-traversal defense (there's no user-controlled path segment to sanitize).

## Rendering mode: every page is `force-dynamic`

Every `page.tsx` (and the root `layout.tsx`) exports `export const dynamic = "force-dynamic"`.
Without it, Next.js's automatic static optimization prerenders pages with no dynamic API usage
(cookies/headers/searchParams) **once at build time** — which would freeze the readiness
percentage, task lists, and blocker counts as of `npm run build`, only updating when a Server
Action's `revalidatePath` happens to touch that route. That's fine for content sites; it's
wrong for a live operational dashboard where an external script (`npm run db:seed`,
`npm run restore`) can change the database without going through a Server Action at all. Verify
this hasn't regressed after touching a page by checking `npm run build`'s route table — every
route should be marked `ƒ (Dynamic)`, not `○ (Static)`.

## Testing strategy

- **Business logic**: `tests/services/*.test.ts` — the readiness/priority/gate/dependency rules
  above, tested as pure functions (see examples in `tests/services/launchGates.test.ts` for the
  "a required milestone that is blocked must not allow Company Ready" class of assertion).
- **Components**: one representative test (`tests/components/status-badge.test.tsx`) — most of
  this app's components are thin, data-driven presentational wrappers around the services
  layer above, which is where the actual logic (and test value) lives.
- **End-to-end**: no Playwright suite. Every flow in the brief's acceptance scenario (mark a
  task done, watch readiness move, capture a note, convert it to a Waiting task, complete a
  15-minute win, check the Roadmap projection move, ask the Copilot what's blocking launch) was
  driven by hand in a real browser against the seeded dataset during development, including a
  full backup → restore round-trip and a production (`next build && next start`) smoke test.
  Adding a maintained Playwright suite on top of that was judged not practical within this
  project's scope (it needs its own server-lifecycle orchestration and fixture-reset strategy
  to be reliable in CI, which is a separate piece of work from the app itself) — it's listed as
  a next improvement in ROADMAP.md rather than bolted on partially.

## Directory layout

```
app/                  routes (App Router) — one folder per top-level nav item, plus app/tasks/[id] and app/api/*
components/
  ui/                  shadcn-style primitives (Button, Card, Dialog, Select, ...)
  layout/               shell: Sidebar, MobileNav, AppShell, ThemeToggle
  setup/, tasks/, blockers/, documents/, costs/, readiness/, roadmap/, focus/, copilot/, settings/, today/
                          feature components, one folder per domain area
lib/
  services/              pure scoring/business logic (see above) — no Prisma imports
  data/                    Prisma → flat-shape adapters (domain.ts, computed.ts, settings.ts)
  actions/                 "use server" mutations, one file per domain area
  db/client.ts             PrismaClient singleton with the SQLite driver adapter
  ai/provider.ts           AIProvider interface + NullAIProvider default + Ollama seam
  backup.ts, backupSchema.ts   export/import logic shared by the API routes and CLI scripts
  storage.ts               local file upload/delete, path-traversal-safe by construction
prisma/
  schema.prisma, migrations/, seed.ts
generated/prisma/         Prisma Client output (gitignored, regenerated on install)
scripts/                  setup.mjs, backup.mjs, reset-demo.mjs, restore.ts — see README
data/                     SQLite database + backups (gitignored)
storage/uploads/          uploaded document files (gitignored)
tests/                    Vitest suites
```
